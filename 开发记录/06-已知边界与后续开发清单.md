# 已知边界与后续开发清单

日期：2026-09-07。本文件记录当前能力边界和下一步建议，不代表这些后续项目已经实现。本次整理只写文档，没有顺带修改代码。

## 1. 明确存在的交付边界

| 项目 | 当前情况 |
| --- | --- |
| 原生范围 | 全部客户端界面使用 WPF；规则仍由 JavaScript 子进程执行 |
| AI 行动语音 | 没有新生成的男女 AI 语音素材；本地缓存缺失时尝试系统语音 |
| 音效与动画 | 筹码 MP3、音乐已迁移；部分提示仍为系统声音，动画不是旧版效果的逐项复刻 |
| 五档场景 | 一张 AI 基础美术经原生校准，并叠加五档轻微色差；不是五个不同房间 |
| WebP | 头像解码依赖 Windows WIC 支持 |
| 外部 AI | 已验证模拟接口和回退逻辑；真实服务、费用、长延迟、现场网络还需实际验证 |
| UI 验收 | 已有真实 WPF 渲染与程序驱动流程；未形成全面的真人输入/系统 UI 自动化矩阵 |
| 存储 | 单个核心 JSON 临时写后替换；没有跨文件事务、完整自动备份或所有损坏类型恢复 |
| UI 架构 | partial 主窗口 + 手工控件布局；没有完整 MVVM、数据绑定和组件生命周期系统 |

## 2. 优先核对的边界场景

下列内容来自本次源码梳理，属于需要专门验证或改进的事项；没有在本次整理中证明每一项都会在正常操作下导致故障。

### A. 外部 AI 请求期间的取消与关闭

bridge 串行等待命令执行，`RulesClient.Call` 也一次只读写一条请求。长时间 `tick` 会让后续 `ai-cancel`、保存或关闭命令排队。

建议：为取消设置独立控制机制，或让异步 AI 任务与命令读取分离；同时保持“旧版本回复不能执行”的校验。验收应覆盖长请求中取消、改配置、下桌、关闭，以及超时之后是否出现迟到行动。

### B. 仅打开弹窗与真正暂停的区别

`Pulse()` 遇到弹层会停止自动推进，但不一定调整服务器行动截止时间。只有显式 `pause` 会在继续时平移计时。

建议先确定产品规则：看档案/设置期间是否暂停玩家倒计时、是否允许房间继续到时。随后把弹层行为和计时规则统一，不要依赖用户关闭弹窗后才发现已经超时。

### C. 金额输入与按钮文字同步

滑块/文本框会更新 `raiseTo`，但加注按钮文字是在 `RenderActions()` 创建时计算的。拖动后按钮显示是否保持同步，应补真人交互验证。

建议金额输入、滑块、按钮文案共享同一可观察值，提交时仍以本地规则检查为准。另验收非法输入、小数、失焦修正和短全下上限。

### D. 暂停恢复及跨程序重启

当前保存 `nativePaused` 和暂停时间；关闭/启动流程会尝试取消暂停。需要分别验证普通关闭、进程异常退出、长时间停机以及操作系统时间改变，不要仅验证同一次运行内暂停几秒。

### E. 职业统计、补位和人物世界的连接

长期统计按 `characterId` 保存，桌内身份却可在两手之间被替换。需要针对离席、补位、再遇见验证最后一手统计不会丢失或混入另一人。

世界模块和桌内人物资金各有推进逻辑；后续若要求严格统一“同一个人的全世界财富”，要明确进桌扣款、离桌回存、工作收入与后台牌局之间的同步契约，不能只把两个数字都叫 bankroll。

### F. 隐藏参数的公开投影

当前 UI 不显示私有策略参数，且外部 AI 有独立的观察对象隔离测试。但“界面不显示”不自动等于“所有响应 JSON 都剔除了私有字段”。

建议专门审计 `visibleCharacter`、公开世界状态、history 和报告的嵌套字段，尤其是 `card`、`playerCard`、`level` 等名称。以明确白名单区分 UI 公共资料、机器人自身可用资料和本机审计数据。

### G. QA 的写入范围与成功判定

`--qa` 会覆盖五张正式场景图，而且成功 JSON 写入早于最后的退出清理。

建议把“美术导出”和“只读渲染验收”拆成独立命令；在整个流程正常结束后再写成功标记。增加操作系统级的按钮/键盘测试，而不只调用界面方法。

### H. 状态查询成本与 UI 重绘

Store 状态查询会刷新世界并写盘，服务封装还可能再次取得状态；WPF 多处通过清空并重建控件刷新。

建议先测量长场次、角色数增加和低性能机器的实际耗时，再将纯查询、世界推进和保存分开；将最频繁变化的倒计时、筹码和输入框改为局部更新。避免在没有测量前盲目增加缓存。

## 3. 后续开发顺序建议

1. 先建立统一的工作副本和版本记录，避免旧项目、staging 与正式目录发生无意覆盖。
2. 补充上述交互与进程生命周期回归，明确暂停、取消、关闭和超时的产品语义。
3. 补齐声音素材；加入真实设备试听与缺失音频测试。
4. 分离 QA 与场景导出，完善 DPI、窗口尺寸和焦点测试。
5. 将动态 JSON 的关键字段逐步转为强类型 DTO，将规则变化与 UI 重绘分离。
6. 增加存档版本号、备份和迁移日志，设计跨文件一致性策略。
7. 若确实需要全部业务 C# 化，再先定义规则一致性样例；将相同牌堆与行动序列分别交给旧/新引擎，逐事件比较筹码和结果，而不是直接替换。
