# 重建过程与开发经验

日期：2026-09-07。详细模块入口见 [架构记录](02-原生架构与内部通信.md)。

## 1. 先识别真正需要重做的部分

旧项目使用 Electron 承载网页界面，但规则、人物、电脑策略、存档和报告已经分布在独立的 JavaScript 模块中。此次需要替换的是界面运行环境、界面组织和前后端通信方式，业务核心并不需要全部重新实现。

最终采用 WPF 界面 + 本地规则子进程。这样可以重做界面，同时保留已有下注规则、边池计算、人物参数与策略行为，减少因为同时重写所有模块而引入的规则偏差。

经验：迁移前先画清依赖关系，区分渲染、调度、规则、状态和素材。不要把“彻底重建游戏结构”简单理解成逐行翻译全部源码。

## 2. 功能文档与当前源码不能混为一谈

文档对功能意图很有价值，但部分条目与实际实现不同。此次核对并修正了以下差异：

| 问题 | 原实现或发现 | 本次处理 |
| --- | --- | --- |
| 人物数量 | 文档总数与 38 + 117 的分项不一致 | 按实际角色库记录为 155 位，保留 38 本地 / 117 AI 分组 |
| 身份竞猜 | 源码一次猜中或两次猜错即可解锁 | 调整为两次猜中、一对两错或三错 |
| 房间到时 | 状态查询可直接结束仍在进行的牌局 | 到时后让当前手完成，随后结算 |
| 强制退出 | 曾继续模拟剩余房间时间对应的额外手牌 | 仅收尾当前手，不创造未来手牌 |
| 跨场记忆 | 新开桌时清空记忆库 | 保留职业记忆并恢复到新场次 |
| 中途退码 | 桌上筹码减少可能被计作牌局亏损 | 增加累计退码与手内筹码调整记账 |
| 空座补位 | 已变为空座的座位不再进入某些重试分支 | 在两手之间继续检查空座和破产座位 |
| 机器人破产 | 缺乏按后手资金继续补码的完整路径 | 增加补码意愿、资金扣除与离席分支 |
| 挂机人数 | 没有完整执行人数上限 | 增加七人 3、五人 2、三人 1、单挑 0 的上限 |
| 历史身份 | 回放可能使用场次最终座位人物 | 优先使用该手保存的 `finalPlayers` |

经验：先用源码和测试确认差异，再决定按需求改变哪一部分。修改了产品行为后，旧测试的断言也需要相应更新，但不能仅为了让测试通过而删掉规则约束。

## 3. 在当前 Windows 环境找到可用构建链

检测到机器安装了 .NET 运行时，但没有 .NET SDK。最终使用 Windows 自带的 .NET Framework 编译器 `csc.exe`，直接编译 C# 源文件并引用 WPF 程序集。

开发中遇到的具体问题：

- `WindowsBase.dll`、`System.Speech.dll` 等文件实际在 Framework 的 `WPF` 子目录，不能把所有程序集都按同一级路径引用。
- Framework 编译器语言版本较旧，某些现代 C# 写法不能直接使用。
- 条件运算符在 `SolidColorBrush` 与 `ImageBrush` 间无法推断共同类型，需要明确转成 `Brush`。
- 同时引入 `System.IO` 与 `System.Windows.Shapes` 后，`Path` 存在歧义；使用完整类型名解决。
- Windows PowerShell 5.1 对无 BOM UTF-8 脚本内的中文处理不稳定，一度造成字符串终止符解析错误。构建脚本的报错文案改用 ASCII，Markdown 则统一保存为 UTF-8。

经验：先检测 SDK、编译器与程序集的真实位置，再选构建方式。不要只根据 `dotnet.exe` 存在就假设机器能够运行 `dotnet build`。

## 4. 原生启动问题需要落盘日志

第一次原生验收时窗口存在，但没有成功创建规则子进程。为初始化异常补充文件日志后，定位到 `.NET ProcessStartInfo.EnvironmentVariables` 在当前宿主环境遇到 `Path` / `PATH` 重复键。

处理方式：测试数据根目录通过进程启动参数传递，避免为这一用途读取并修改整套环境变量。规则进程仍支持环境变量作为后备，但当前原生客户端优先传启动参数。

另一个问题是无音频输出设备的验收环境中，`SpeechSynthesizer` 在退出清理时才抛异常。将语音清理作为可失败的附属操作处理后，音频不可用不会阻止程序退出。

经验：空白窗口不一定是渲染问题。初始化、子进程创建、协议读写、声音设备和退出路径都需要各自可定位的日志；不要只在界面上显示一条转瞬即逝的状态文字。

## 5. 内部协议要处理不同语言的空值差异

C# 客户端默认会发送 `body: null`，旧 JavaScript 调度器则用 `body === undefined` 区分查询命令与修改命令，导致查询被当作非法请求。

在桥接层统一把 `null` 转为 `undefined` 后恢复正常。桥接层成为兼容边界，而不是要求每个界面调用都记住旧实现细节。

经验：跨语言协议需明确空值、整数、字符串编码、错误响应和消息边界；“都是 JSON”不代表语义天然一致。

## 6. AI 美术生成与精确布局分工

美术需求经历了这些明确调整：

1. 从原先带透视的背景转为严格俯视牌桌。
2. 增加人字拼木地板的木纹、接缝和光照细节。
3. 在桌面加入蓝红叠放扑克牌图标与两行 AFTERHOURS / POKER CLUB。
4. 按参考图重新确定桌面占画面的比例及 Logo 中心。
5. 在 Logo 第二行右侧加入 ™。

内置 ImageGen 能生成所需风格，但多次生成仍出现桌子过高、过扁或 Logo 偏移的问题。最终保留 AI 美术源，再由 WPF 场景绘制按固定锚点校准，输出可复用的本地图。

部分输入图片无法被工具稳定读取，先解码并转换为正常 JPEG 后完成引用。经验是不要仅凭 `.png` 后缀判断图片一定可以被所有读取链路处理。

最有价值的分工：AI 负责材质与图形设计；代码负责精确尺寸、交互坐标、分层和缩放。不要把玩家头像、扑克牌、金额或按钮直接生成进背景图。

## 7. 编译成功之后必须看真实渲染结果

原生验收曾发现：详细复盘列表遮住了公共牌，原因是把 `Grid.SetRow` 设置在内容面板上，而真正加入父 Grid 的对象是包裹它的 ScrollViewer。修改行定位对象后解决。

还对长人物姓名、精简复盘背景透明度、桌面操作区位置和详细事件列表进行了调整。验收输出九张 PNG，避免只凭代码推断布局。

经验：每个布局属性都要作用于真正的布局子元素。滚动容器、嵌套 Grid 和 Viewbox 组合尤其容易出现“代码看起来正确、渲染却错位”的问题。

## 8. 在正式目录再验收一次

开发先在 `POKER/native-stage` 进行，验证后新建 `Desktop/AfterHours` 并复制程序、运行时、素材、源码和存档副本。随后在安装目录再次执行规则测试与 `--qa`。

经验：开发目录通过不等于交付目录通过。遗漏运行时、相对路径依赖、缺少素材、错误工作目录都可能只在复制后暴露。
